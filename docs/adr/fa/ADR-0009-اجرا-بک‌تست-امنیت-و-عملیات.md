# ADR-0009: اجرا، بک‌تست، امنیت و عملیات

- **وضعیت:** پیشنهادی (Proposed)
- **تاریخ:** 2026-02-14
- **تصمیم‌گیرندگان:** معمار فنی، مسئول عملیات
- **ADRهای مرتبط:** 0001، 0003، 0008

---

## ۱. زمینه

این ADR مسیر بک‌تست ← کاغذی ← زنده را قابل حسابرسی و امن می‌کند، نحوه اجرای سفارش در بازارهای اسپات نوبیتکس را تعریف می‌کند و وضعیت امنیتی/عملیاتی معاملات خودکار ۲۴/۷ را تنظیم می‌نماید.

## ۲. طراحی اجرا
1. **ماشین حالت مدیر سفارش:** `PLANNED → RISK_CHECKED → SUBMITTED → OPENED → (جزئی) FILLED → چرخه‌حیات TP/SL → CLOSED`، پایدار در DB؛ هر گذار لاگ می‌شود.
2. **ایدم‌پوتنسی:** `clientOrderId` قطعی (ADR-0003). هنگام تایم‌اوت، پیش از هر ارسال مجدد، وضعیت سفارش استعلام می‌شود.
3. **سیاست نوع سفارش:** پیش‌فرض ورود **لیمیت** نزدیک بهترین bid/ask با TTL و ردیابی محدود؛ سفارش **مارکت** فقط برای استاپ/خروج یا حالت سریع صریح. مدیریت پرشدگی جزئی با Polling وضعیت و پنجره مهلت؛ باقی‌مانده پرنشده پس از TTL لغو می‌گردد.
4. **تطابق هنگام راه‌اندازی:** واکشی سفارش‌ها/پوزیشن‌ها/موجودی‌های باز از صرافی؛ بازسازی وضعیت محلی؛ در صورت ناسازگاری هشدار + مسدودشدن ورودهای جدید تا سازگاری.
5. **موتور معامله کاغذی:** همان جریان زنده دفتر سفارش را مصرف می‌کند؛ پرشدگی بر اساس قدم‌زدن در دفتر شبیه‌سازی می‌شود (محافظه‌کارانه: اعمال لغزش + کارمزد) — نتایج کاغذی ساختاراً بدبینانه‌اند نه خوش‌بینانه.
6. **دروازه‌های ارتقا به نسخه زنده** (همه باید پاس شوند):
   - بک‌تست: PF > ۱٫۳، MDD < ۱۵٪، ≥۱۰۰ معامله، سازگاری Walk-Forward در رژیم‌های مختلف.
   - کاغذی: ≥۳۰ روز متوالی، PF روی داده زنده > ۱٫۲، بدون حادثه بحرانی.
   - تأیید دستی + مرحله حجم‌خرد (مواجهه ≤۱٪ سرمایه در روز) حداقل ۲ هفته پیش از افزایش تا سقف‌ها (ADR-0008).

## ۳. بک‌تست و اعتبارسنجی
- دو موتور: تحقیق برداری (vectorbt) برای سرعت؛ شبیه‌ساز رویدادمحور برای ارزیابی نهایی (تا حد ممکن همان مسیر کد مدیر سفارش زنده).
- هزینه‌ها مدل‌شده: تیزهای کارمزد سازنده/گیرنده نوبیتکس (قابل پیکربندی)، لغزش مبتنی بر عمق.
- **مجموعه ضدبیش‌برازش:** تحلیل Walk-Forward، CV با Purge/Embargo برای ویژگی‌های ML، نقشه‌های حرارتی حساسیت پارامتر، درهم‌ریختن مونت‌کارلوی معاملات، نمونه‌خارجی قفل‌شده (۲۰٪ اخیر).
- گزارش‌ها: سرمایه، افت، PF، امیدریاضی، نرخ موفقیت، مواجهه، تفکیک به‌ازای نماد/رژیم؛ ذخیره به‌ازای هر اجرا با هش پیکربندی.

## ۴. امنیت
- **احراز:** کلید API با Ed25519، **فقط دامنه READ + TRADE، بدون برداشت** (ADR-0003). حالت توکن پشتیبانی می‌شود اما توصیه نمی‌گردد.
- **اسرار:** متغیرهای محیطی / Keychain سیستم‌عامل / Docker Secrets؛ `.env` در `.gitignore`؛ هرگز لاگ نمی‌شود؛ دستورالعمل چرخش کلید.
- **سخت‌سازی میزبان:** اجرای کانتینر به‌عنوان غیر-root، لیست سفید IP خروجی در صورت امکان، فعال‌سازی 2FA در حساب نوبیتکس، اتصال کلید API به دستگاه/IP از پنل نوبیتکس.
- **دسترسی به کنترل‌های ربات:** FastAPI پشت توکن احراز؛ دستورات تلگرام با لیست سفید شناسه کاربر.
- **داده:** رمزنگاری DB در حالت سکون (LUKS/ولوم)، بکاپ‌های رمزنگاری‌شده.
- **زنجیره تأمین:** وابستگی‌های پین‌شده با هش، ایمیج‌های پایه مینیمال، `pip-audit` در CI.

## ۵. پایش‌پذیری و عملیات
- **متریک‌ها:** تأخیر چرخه، نرخ خطای اندپوینت‌ها، زمان چرخه‌حیات سفارش، پرشدگی‌ها، لغزش نسبت به میانی، سود/زیان، وضعیت کلید اضطراری (Prometheus → Grafana).
- **لاگ‌ها:** JSON ساخت‌یافته، سطح به‌ازای هر ماژول، نگهداری ۳۰ تا ۹۰ روز؛ فیلتر پاک‌سازی اسرار.
- **هشدارها (تلگرام):** پرشدگی‌ها، توقف‌ها، بریکر مدار، خلاصه روزانه، ازدست‌رفتن ضربان قلب (واچ‌داگ هر ۶۰ ثانیه پینگ می‌زند).
- **استقرار:** docker-compose شامل `bot`, `scheduler`, `postgres+timescale`, `redis`, `api`, `prometheus/grafana`. راه‌اندازی تک‌دستوری؛ ماونت `config/`؛ Healthcheck؛ ریستارت خودکار.
- **CI/CD:** Lint + mypy + تست واحد (پوشش ≥۸۵٪ برای هسته) + تست‌های قراردادی آداپتور + مجموعه رگرسیون بک‌تست؛ تگ‌ها بیلد ایمیج را هدایت می‌کنند.
- **Runbookها:** پلی‌بوک حادثه، چرخش کلید، مدیریت نگهداری صرافی، روی‌های خنثی‌سازی دستی.

## ۶. پیامدها
**مثبت:** هیچ سرمایه زنده‌ای پیش از شواهد؛ اقتصاد صادقانه (کارمزد/لغزش)؛ وضعیت امن برای خودکارسازی؛ بازگشت‌پذیری در هر مرحله (لغو همه، بازگشت به کاغذی).
**منفی:** بار عملیاتی (پایش، Runbookها) جزئی نیست — برای سرمایه ۲۴/۷ در معرض ریسک، ضروری است.
