# ADR-0049 — هشدار شرطی قیمت و پرمیوم بدون مسیر معامله

**فارسی** · [English](../en/ADR-0049-conditional-price-alerts.md)

**وضعیت:** پذیرفته؛ بک‌اند در ۲٫۴٫۰ و اتصال پنل bell در تغییرات محلی پس از آن
**تاریخ:** ۲۰۲۶-۱۱-۰۴
**مرتبط:** ADR-0003، ADR-0011، ADR-0014، ADR-0018 و ADR-0041

## زمینه

Telegram فقط رویدادهای عملیاتی و digest را ارسال می‌کند و دکمهٔ alerts در صفحه هنوز یک موتور هشدار عمومی نیست. Roadmap مورد A5 هشدار قیمت/پرمیوم را می‌خواهد، اما اتصال مستقیم یک تایمر به Telegram بدون freshness و قواعد پایدار می‌تواند هشدار تکراری، دیرهنگام یا ساختگی بسازد.

## تصمیم

قاعده شامل `symbol`، `metric` (`last` یا `premium_pct`)، جهت (`above`/`below`) و آستانه است. قواعد و رویدادها در همان `journal.db` نگهداری می‌شوند تا backup/restore فعلی آن‌ها را نیز پوشش دهد. API خواندن فقط برای Owner/Operator است و ساخت، فعال/غیرفعال یا حذف قاعده session با نقش Operator/Owner و CSRF می‌خواهد. Viewer هیچ دسترسی عملیاتی جدیدی نمی‌گیرد.

ارزیابی فقط روی snapshot فعلی `/market/stats` و timestamp منبع انجام می‌شود. scheduler فوق‌العادهٔ exchange فقط وقتی حداقل یک قاعدهٔ فعال وجود دارد اجرا می‌شود؛ بدون قاعده هیچ درخواست تازه‌ای ارسال نمی‌شود. قیمت مستقیم برای همهٔ بازارهای دریافت‌شده نگه داشته می‌شود، در حالی که خروجی عمومی universe همچنان top-60 است. پرمیوم USDTIRT فقط از سه بازار مرجع و قدیمی‌ترین timestamp آن‌ها سنجیده می‌شود.

اولین مشاهدهٔ تازه فقط قاعده را arm می‌کند و هشدار نمی‌فرستد. trigger فقط هنگام عبور از وضعیت false به true رخ می‌دهد؛ ماندن بالاتر/پایین‌تر از آستانه تکرار ندارد. دادهٔ مفقود، نامعتبر، آینده یا stale قاعده را disarm می‌کند. بازگشت از outage اول یک baseline تازه می‌سازد و هشدار دیرهنگام تولید نمی‌کند. timestamp تکراری یا قدیمی‌تر نمی‌تواند رویداد دوم بسازد و ذخیرهٔ رویداد و انتقال state در یک تراکنش اتمیک است.

trigger و delivery دو واقعیت جداگانه‌اند. رویداد پیش از تماس Telegram ثبت می‌شود؛ سپس نتیجهٔ `sent` و یک reason محدود و بدون متن خطای بیرونی ذخیره می‌شود. crash یا شکست تحویل به retry کور و پیام تکراری تبدیل نمی‌شود. حذف قاعده، رویدادهای تاریخی را با snapshot همان قاعده نگه می‌دارد.

این تصمیم هیچ سفارش Paper/Live، تغییر ریسک، تغییر execution mode یا مجوز Viewer ایجاد نمی‌کند. دکمهٔ bell در تغییرات محلی پس از ۲٫۴٫۰ به همین API متصل شده است: خواندن فقط با بازکردن/refresh پنل توسط Owner/Operator، mutation با session/CSRF، حذف دومرحله‌ای، نمایش arming/freshness/delivery و ابطال cache هنگام تغییر هویت انجام می‌شود. badge فقط تعداد rule فعال است و UI polling مستقل یا مسیر سفارش ندارد.

## پیامدها

- دادهٔ stale می‌تواند باعث «هشدار نشدن» شود؛ این تصمیم عمدی و ترجیح آن بر هشدار غیرقابل‌اعتماد است.
- تحویل ناموفق در event قابل مشاهده است اما retry خودکار ندارد؛ سیاست retry در صورت نیاز به ADR جداگانه و idempotency مشخص نیاز دارد.
- قواعد در سطح حساب مشترک‌اند، نه watchlist شخصی هر کاربر.
