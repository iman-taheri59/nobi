# ADR-0028 — مرز امن اجرای واقعی: امضا پیش از سفارش

[English](../en/ADR-0028-safe-live-execution-boundary.md) · **فارسی**

**وضعیت:** پذیرفته‌شده — مرحله B1 در ۱٫۲٫۱ پیاده شد؛ ارسال سفارش واقعی همچنان خاموش
**تاریخ:** ۲۰۲۶-۱۰-۲۵
**مرتبط:** ADR-0003، ADR-0008، ADR-0009، ADR-0014، ADR-0027

## زمینه

API Key نوبیتکس سه هدر `Nobitex-Key`، `Nobitex-Signature` و `Nobitex-Timestamp` می‌خواهد. متن امضا دقیقاً `timestamp + METHOD + full_path + raw_body` و امضا Ed25519 با Base64 URL-safe است. کوچک‌ترین تفاوت میان بدنهٔ امضاشده و بدنهٔ ارسالی درخواست را نامعتبر می‌کند. افزودن مستقیم این منطق به کلاینت عمومی، مرز فقط‌خواندنی فعلی را مبهم و احتمال نشت secret یا ارسال ناخواسته را زیاد می‌کند.

## نیازمندی‌های B1

1. signer تابعی مستقل و بدون شبکه باشد و فقط bytes نهایی بدنه را امضا کند.
2. query string بخشی از `full_path` و ترتیب/encoding آن همان مسیر ارسالی باشد.
3. private key فقط از environment/secret store وارد حافظه شود؛ هرگز log، repr، diagnostics، backup یا مرورگر نشود.
4. خطای کلید، timestamp و Base64 پیش از شبکه رخ دهد.
5. آزمون، امضا را با کلید عمومی Ed25519 تأیید و تغییر هر جزء payload را رد کند.
6. افزودن signer به‌تنهایی هیچ endpoint معامله، route یا feature flag را روشن نکند.

## تصمیم

ماژول `server/nobitex_signing.py` تنها مرجع ساخت payload و هدر امضاشده است. ورودی آن کلید عمومی، private key URL-safe Base64، method، full path، raw body و timestamp است. JSON در این ماژول ساخته نمی‌شود؛ caller باید یک raw body ثابت را هم امضا و هم ارسال کند.

مرحله بعد یک `LiveExecutionClient` جدا از `NobitexClient` عمومی خواهد بود. تا ADR بعدی و تکمیل idempotency/reconciliation، `_auth_headers` فعلی و همه مسیرهای live خاموش می‌مانند.

## معیار پذیرش

- امضای تولیدشده با public key متناظر verify شود؛
- تغییر timestamp، method، path یا body verify را شکست دهد؛
- کلید ۳۲ بایتی نامعتبر و Base64 خراب با پیام فاقد secret رد شود؛
- هیچ route موجود و execution mode تغییر نکند؛
- تمام gateهای قبلی سبز بمانند.
