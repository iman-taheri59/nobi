# نسخه‌بندی و انتشار nobitrader

**فارسی** · [English](releases.en.md)

نسخهٔ جاری **2.0.8** است؛ وضعیت انتشار واقعی را در Releases بررسی کنید. انتشار این نسخه فقط پس از سبزشدن CI همان commit انجام می‌شود؛ وضعیت واقعی را در Releases بررسی کنید. `VERSION` مرجع شمارهٔ انتشار است؛ نام تگ دقیقاً `v` به‌علاوهٔ همان شماره است.

برای مسیر قبلیِ ارتقای ۲٫۰٫۰ به ۲٫۰٫۱، [طرح ارتقای سازگار کد و داده](upgrade-2.0.1.md) را پیش از ساخت/اجرای نصبگر بررسی کنید؛ نصبگر ۲٫۰٫۰ صرفاً با تغییر TAG برای این مسیر کافی نیست.

## قواعد از این پس

- هر مجموعه تغییر، حتی تغییر مستندات، یک افزایش نسخه و یک بخش جدید در `CHANGELOG.md` و `CHANGELOG.en.md` دارد.
- اصلاح معمول: PATCH، برای مثال `1.0.9` به `1.0.13`.
- قابلیت جدید سازگار: MINOR، برای مثال `1.0.1` به `1.1.0`.
- تغییر ناسازگار: MAJOR، برای مثال `1.0.1` به `2.0.0`.
- شماره در `VERSION`، `server/main.py`، `package.json`، دو محل نسخهٔ بسته در `package-lock.json`، نشان نسخهٔ وب و خروجی مستقل باید یکسان باشد. شمارهٔ نسخهٔ وابستگی‌ها و API صرافی ربطی به نسخهٔ محصول ندارد.
- یک تگ annotated روی همان کامیت نسخه ساخته می‌شود. تگ منتشرشده هرگز جابه‌جا، حذف یا force-push نمی‌شود؛ اصلاح بعدی نسخهٔ جدید می‌گیرد.
- نام محصول در مستندات `nobitrader` است. املای فعلی رابط `nobiTrader` باقی می‌ماند. نام Nobitex نام صرافی است و عوض نمی‌شود.

## چه چیزی PATCH است و چه چیزی MINOR

SemVer شمارهٔ سوم را «شمارنده» نمی‌بیند؛ شمارهٔ **نوع تغییر** است. پس تصمیم با جنس تغییر گرفته می‌شود، نه با تعداد نسخه‌های قبلی:

| تغییر | شماره |
|---|---|
| مستند، ADR، CHANGELOG، آزمون، بازآرایی داخلی، یا اصلاح رفتار اشتباه | PATCH — مثال: `1.0.30` → `1.0.31` |
| قابلیت تازه‌ای که **همچنان در سایه است**: عدد و شاهد اضافه می‌کند ولی کاری که کاربر می‌تواند بکند عوض نمی‌شود و `applied:false` می‌ماند | PATCH (استثنای صریح دورهٔ سایه) |
| **رفتار معاملاتی** عوض می‌شود: دروازه‌ای واقعاً فیلتری می‌کند، آستانه‌ای اعمال می‌شود، سیگنال یا پوزیشن می‌تواند متفاوت شود | MINOR — `1.1.0` → `1.1.0` |
| رابط یا API ناسازگار عوض می‌شود | MAJOR — `1.9.10` → `2.0.0` |

قاعدهٔ ساده: تا وقتی هیچ دروازه‌ای ردیفی را رد نمی‌کند، دورهٔ سایه است و PATCH کافی است. اولین دروازه‌ای که واقعاً فیلتر کند، MINOR است — در این پروژه یعنی قدم S6 از ADR-0023.

## سقف شماره‌ها

عدد باید خوانا بماند، پس هر فیلد سقف دارد. سقف، **بیشترین مقدار مجاز** است نه تعداد نسخه‌ها؛ یعنی `1.1.0` مجاز است و انتشارِ **بعد از** آن `1.1.0` می‌شود.

| فیلد | سقف | وقتی به سقف رسید |
|---|---|---|
| PATCH — تا اولین عبور از خط `1.0.x` | ۳۰ | انتشار بعدی `1.1.0`؛ PATCH صفر می‌شود |
| PATCH و MINOR — از `1.1.0` به بعد | ۱۰ | انتشار بعدی، فیلد بالاتر را یکی بالا می‌برد و فیلد پایین‌تر صفر می‌شود: `1.1.10` → `1.2.0` و `1.10.4` → `2.0.0` |
| MAJOR | ۱۰ | `10.x.y` مجاز است؛ بعد از آن `11.0.0` |

- پرش اجباری از PATCH به MINOR **یعنی تغییر بزرگ نبوده**؛ فقط سقف پر شده. در `CHANGELOG` همان نسخه بنویسید «افزایش نسخه به‌خاطر سقف، نه تغییر رفتار».
- سقف با آزمون کنترل می‌شود (`server/tests/test_release_version.py`) تا شمارهٔ بیرون از قاعده در CI رد شود.
- اگر روزی لازم شد سقفی عوض شود، همین جدول و همان آزمون با هم عوض می‌شوند؛ سقف یک قرارداد است، نه عادت.

## ساخت و بررسی

از ریشهٔ پروژه:

```sh
npm ci --no-audit --no-fund
npm run build
python scripts/release_notes.py --tag v2.0.8
python -m pytest -q server/tests
npm run test:display
npm run lint
npm run lint:dashboard
```

دستورهای آزمون پایتون به وابستگی‌های `server/requirements-dev.txt` نیاز دارند. دستور `release_notes.py` بدون تماس با GitHub، تطابق تگ با نسخه و وجود یادداشت همان نسخه را کنترل می‌کند. شمارهٔ تگ در نمونه‌های این صفحه، مخصوص همین انتشار است؛ در انتشار بعدی آن را مطابق `VERSION` عوض کنید.

## کامیت، تگ و پوش

این دستورها فقط نمونهٔ انتشارند، نه مجوز اجرا. پس از بازبینی و آزمون، **اجازهٔ صریح کاربر برای push/انتشار همین نسخه** لازم است. قاعدهٔ عادی ارسال هم‌زمان شاخه و تگ annotated همان commit است:

برای انتشار تأییدشدهٔ **۲٫۰٫۳** استثنا برقرار است: ابتدا فقط `main` را برای CI ارسال کنید؛ پس از موفقیت گیت‌های لازم روی همان commit و بررسی عدم جابه‌جایی شاخه، تگ annotated همان commit و سپس Release منتشر می‌شود. این مجوز شامل نصب یا سفارش نیست. دستور ارسال هم‌زمان زیر قاعدهٔ عمومی است، نه روند این انتشار.

```sh
git tag -a v2.0.8 -m "nobitrader 2.0.8"
git push origin main v2.0.8
```

اگر تگ از قبل وجود دارد، دوباره نسازید یا جابه‌جا نکنید؛ با `git show v2.0.8 --no-patch` مقصد آن را بررسی کنید. اعتبارسنجی workflow تگ نیز باید موفق شود؛ سبزبودن CI شاخه جای آن را نمی‌گیرد. این روند مجوز نصب روی سرور نیست.

استثنای دو مرحله‌ایِ تأییدشده برای ۲٫۰٫۱ (main، سپس CI سبز، سپس تگ/Release) تاریخی و مربوط به همان انتشار است؛ به ۲٫۰٫۲ یا انتشار آینده تعمیم داده نمی‌شود. تگ منتشرشدهٔ ۲٫۰٫۱ تغییر نمی‌کند.

## GitHub Release

فایل `.github/workflows/release.yml` فقط هنگام پوش تگ نسخه اجرا می‌شود:

1. ساخت نسخهٔ مستقل و کنترل تازگی خروجی‌ها؛
2. تطابق شمارهٔ تگ، نسخه‌های محصول و یادداشت تغییرات، و اجرای آزمون‌ها؛
3. ساخت Release با عنوان `nobitrader vX.Y.Z` و متن بخش همان نسخه در changelog؛
4. پیوست `nobitrader-mobile.html`؛ GitHub آرشیو کد همان تگ را نیز در دسترس می‌گذارد.

مجوز نوشتن فقط به job انتشار داده می‌شود و از `GITHUB_TOKEN` موقت Actions استفاده می‌کند؛ PAT در مخزن یا workflow ذخیره نمی‌شود. اگر سیاست مخزن/سازمان نوشتن Release با این توکن را محدود کند، اجرای Actions خطا می‌دهد و باید همان سیاست بررسی شود. پوش به‌تنهایی به معنی موفقیت Release نیست؛ نتیجه را در Actions و صفحهٔ Releases بررسی کنید. انتشار idempotent است: اگر Release همان تگ از قبل وجود داشته باشد، گام انتشار به‌جای شکستن روی «از قبل وجود دارد»، یادداشت‌ها را با `gh release edit` به‌روز می‌کند و فایل موبایل را با `gh release upload --clobber` دوباره می‌فرستد؛ هر دو مسیر پیش از انتشار بررسی می‌کنند که تگ به همان کامیتِ checkout‌شده اشاره کند. این روند، استقرار روی سرور آروان را انجام نمی‌دهد.

## نام‌های فنی قدیمی

آدرس واقعی مخزن همچنان `https://github.com/iman-taheri59/nobi.git` است؛ تغییر نام آن از محدودهٔ اصلاح مستندات خارج است. همین‌طور نام سرویس `nobi`، مسیرهای واقعی `/opt/nobi`، `/etc/nobi` و `/srv/nobi-data` با فایل‌های نصب موجود مطابقت دارند و عمداً حفظ شده‌اند. جایگزین‌کردن این شناسه‌ها فقط در متن، دستورهای استقرار را خراب می‌کند.

نام پوشه و دامنه در مثال‌های نصب جدید ویندوز اکنون `nobitrader` و `nobitrader.test` است. برای نصب موجود لازم نیست پوشه یا سرویس خود را جابه‌جا کنید؛ دستورها را با مسیر واقعی نصب خود اجرا کنید.
