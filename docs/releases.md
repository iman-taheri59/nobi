# نسخه‌بندی و انتشار nobitrader

**فارسی** · [English](releases.en.md)

نسخهٔ جاری این تغییر **1.0.9** است؛ تگ منتشرشدهٔ قبلی **v1.0.6** است و تگ این تغییر **v1.0.9** خواهد بود. `VERSION` مرجع شمارهٔ انتشار است؛ نام تگ دقیقاً `v` به‌علاوهٔ همان شماره است.

## قواعد از این پس

- هر مجموعه تغییر، حتی تغییر مستندات، یک افزایش نسخه و یک بخش جدید در `CHANGELOG.md` و `CHANGELOG.en.md` دارد.
- اصلاح معمول: PATCH، برای مثال `1.0.8` به `1.0.9`.
- قابلیت جدید سازگار: MINOR، برای مثال `1.0.1` به `1.1.0`.
- تغییر ناسازگار: MAJOR، برای مثال `1.0.1` به `2.0.0`.
- شماره در `VERSION`، `server/main.py`، `package.json`، دو محل نسخهٔ بسته در `package-lock.json`، نشان نسخهٔ وب و خروجی مستقل باید یکسان باشد. شمارهٔ نسخهٔ وابستگی‌ها و API صرافی ربطی به نسخهٔ محصول ندارد.
- یک تگ annotated روی همان کامیت نسخه ساخته می‌شود. تگ منتشرشده هرگز جابه‌جا، حذف یا force-push نمی‌شود؛ اصلاح بعدی نسخهٔ جدید می‌گیرد.
- نام محصول در مستندات `nobitrader` است. املای فعلی رابط `nobiTrader` باقی می‌ماند. نام Nobitex نام صرافی است و عوض نمی‌شود.

## ساخت و بررسی

از ریشهٔ پروژه:

```sh
npm ci --no-audit --no-fund
npm run build
python scripts/release_notes.py --tag v1.0.9
python -m pytest -q server/tests
npm run test:display
npm run lint
npm run lint:dashboard
```

دستورهای آزمون پایتون به وابستگی‌های `server/requirements-dev.txt` نیاز دارند. دستور `release_notes.py` بدون تماس با GitHub، تطابق تگ با نسخه و وجود یادداشت همان نسخه را کنترل می‌کند. شمارهٔ تگ در نمونه‌های این صفحه، مخصوص همین انتشار است؛ در انتشار بعدی آن را مطابق `VERSION` عوض کنید.

## کامیت، تگ و پوش

پس از بازبینی و موفقیت تست‌ها، تغییرات مرتبط را commit کنید و سپس:

```sh
git tag -a v1.0.9 -m "nobitrader 1.0.9"
```

فقط پس از اجازهٔ push:

```sh
git push --atomic origin main v1.0.9
```

اگر تگ از قبل ساخته شده است، دوباره `git tag` نزنید. قبل از پوش، با `git show v1.0.9 --no-patch` مقصد تگ را بررسی کنید. `--atomic` مانع انتشار نصفهٔ شاخه/تگ در صورت رد یکی از آن‌ها می‌شود.

## GitHub Release

فایل `.github/workflows/release.yml` فقط هنگام پوش تگ نسخه اجرا می‌شود:

1. ساخت نسخهٔ مستقل و کنترل تازگی خروجی‌ها؛
2. تطابق شمارهٔ تگ، نسخه‌های محصول و یادداشت تغییرات، و اجرای آزمون‌ها؛
3. ساخت Release با عنوان `nobitrader vX.Y.Z` و متن بخش همان نسخه در changelog؛
4. پیوست `nobitrader-mobile.html`؛ GitHub آرشیو کد همان تگ را نیز در دسترس می‌گذارد.

مجوز نوشتن فقط به job انتشار داده می‌شود و از `GITHUB_TOKEN` موقت Actions استفاده می‌کند؛ PAT در مخزن یا workflow ذخیره نمی‌شود. اگر سیاست مخزن/سازمان نوشتن Release با این توکن را محدود کند، اجرای Actions خطا می‌دهد و باید همان سیاست بررسی شود. پوش به‌تنهایی به معنی موفقیت Release نیست؛ نتیجه را در Actions و صفحهٔ Releases بررسی کنید. انتشار idempotent است: اگر Release همان تگ از قبل وجود داشته باشد، گام انتشار به‌جای شکستن روی «از قبل وجود دارد»، یادداشت‌ها را با `gh release edit` به‌روز می‌کند و فایل موبایل را با `gh release upload --clobber` دوباره می‌فرستد؛ هر دو مسیر پیش از انتشار بررسی می‌کنند که تگ به همان کامیتِ checkout‌شده اشاره کند. این روند، استقرار روی سرور آروان را انجام نمی‌دهد.

## نام‌های فنی قدیمی

آدرس واقعی مخزن همچنان `https://github.com/iman-taheri59/nobi.git` است؛ تغییر نام آن از محدودهٔ اصلاح مستندات خارج است. همین‌طور نام سرویس `nobi`، مسیرهای واقعی `/opt/nobi`، `/etc/nobi` و `/srv/nobi-data` با فایل‌های نصب موجود مطابقت دارند و عمداً حفظ شده‌اند. جایگزین‌کردن این شناسه‌ها فقط در متن، دستورهای استقرار را خراب می‌کند.

نام پوشه و دامنه در مثال‌های نصب جدید ویندوز اکنون `nobitrader` و `nobitrader.test` است. برای نصب موجود لازم نیست پوشه یا سرویس خود را جابه‌جا کنید؛ دستورها را با مسیر واقعی نصب خود اجرا کنید.
