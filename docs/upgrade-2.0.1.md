# طرح ارتقای امن از ۲٫۰٫۰ به ۲٫۰٫۱

**فارسی** · [English](upgrade-2.0.1.en.md)

> پیش‌نویس عملیاتی پیش از انتشار؛ دستور نصب یا اجازهٔ اجرا نیست. نسخهٔ منتشرشدهٔ فعلی ۲٫۰٫۰ است. اجرای واقعی systemd/ارتقا/rollback برای ۲٫۰٫۱ هنوز انجام نشده است.

## چرا نصبگر قبلی کافی نیست؟

اصلاحیه قرارداد قیمت IRT در REST UDF، کندل WS و tick را تصحیح می‌کند و ستون `price_contract` و view `signal_evidence` را به ژورنال می‌افزاید. تاریخچهٔ IRT با واحد نامعلوم بدون بازنویسی حفظ ولی از شواهد معتبر کنار گذاشته می‌شود.

اسکریپت مستقل نصب ۲٫۰٫۰ که قبلاً به کاربر تحویل داده شد، در مسیر خطا فقط source را برمی‌گرداند و ممکن است با state جدید سرویس قدیمی را دوباره اجرا کند. **آن اسکریپت با تعویض TAG و hash، نصبگر امن ۲٫۰٫۱ نمی‌شود.** بازگشت این ارتقا نیازمند تصمیم آگاهانه دربارهٔ قرارداد کد و داده است.

## دروازه‌های پیش از نصب

1. هویت نویسنده، commit نهایی و اجازهٔ push مشخص باشد؛ تمام CIهای الزامی همان commit سبز شوند. انتشار موفق و تگ annotated `v2.0.1` به همان commit تأیید شود. نتیجهٔ محلی جای CI را نمی‌گیرد.
2. commit و SHA256 واقعی فایل مستقل از انتشار تأییدشده در نصبگر نهایی تثبیت شوند؛ فایل حاوی placeholder یا hash حدسی اجرا نشود.
3. وضعیت سرویس، نسخه، مسیر واقعی state و تنظیمات فعلی فقط محلی بررسی شوند. `.env`، توکن، فایل‌های auth و backup خصوصی نباید در گفتگو یا لاگ عمومی چاپ/ارسال شوند.
4. با تأیید خود کاربر پنجرهٔ نگهداری تعیین و تب‌های قدیمی بسته شوند. درخواست سفارش/تغییر تنظیمات هم‌زمان با نصب پذیرفته نشود؛ Live/Auto یا caps خودکار تغییر نکنند.
5. پس از توقف کنترل‌شدهٔ سرویس و writerهای مربوط، state محلی دوباره بررسی شود. پیش‌فرض این ارتقا **عدم وجود پوزیشن یا سفارش فعال** است؛ گزارش قدیمیِ «پوزیشن باز ندارم» کافی نیست. در صورت وجود، نصب متوقف و همان نسخهٔ قبلی بدون دست‌کاری state بازگردانده شود؛ خروج اجباری، تغییر استاپ یا ×۱۰کردن قیمت‌ها ممنوع است. به‌خصوص پوزیشن IRT قدیمی خودکار مهاجرت واحد ندارد.
6. dirty بودن tracked source، ناشناخته‌بودن مسیر state، نبودن فایل موردانتظار، backup نامعتبر یا عدم امکان توقف writer موجب توقف نصب باشد؛ پوشاندن خطا با نصب تازه/حذف داده ممنوع است.

## snapshot منسجمِ پیش از تغییر

در دایرکتوری خصوصی با دسترسی محدود و مالکیت مناسب ثبت شود:

- commit/tag قبلی، source همان commit و شناسهٔ نسخه؛
- نسخهٔ قابل‌بازیابی محیط اجرا و فهرست وابستگی‌ها؛ در این اصلاحیه requirements محصول تغییر نکرده‌اند، اما rollback نباید به فرضِ سازگاری نامعلوم متکی باشد؛
- نسخهٔ خصوصی تنظیمات و واحد سرویس، و hash برای کنترل عدم تغییر؛ بدون چاپ محتوای secret؛
- مسیرهای مؤثر `journal.db`، `auth.db`، `live_execution.db`، Paper و سایر stateهای پیکربندی‌شده؛ صرفاً فرض‌کردن `/srv/nobi-data` کافی نیست؛
- snapshot سالم SQLite با API backup و `integrity_check`؛ کپی فایل database زنده به‌تنهایی معتبر نیست؛
- Paper JSON **همراه `.bak` متناظر**، و stateهای اجرای/اسکن پیکربندی‌شده؛ فقدان فایل به‌طور صریح ثبت شود تا فایل جدید با backup قدیمی اشتباه نشود.

ابزار `scripts/state_backup.py` تنها سه پایگاه SQLite را پوشش می‌دهد؛ Paper، `.bak`، config خصوصی و source خارج از آن‌اند. عبارت `contains_secrets:false` در manifest مجوز انتشار archive نیست: این پایگاه‌ها می‌توانند دادهٔ حساب/کاربر داشته باشند و باید خصوصی بمانند.

## اعمال و بررسی اولیه

- فقط source تأییدشده با روش fast-forward یا checkout کنترل‌شدهٔ همان commit نصب شود؛ local changes با reset اجباری از بین نروند.
- hash فایل مستقل و عدم تغییر تنظیمات بررسی شود. migration ژورنال افزایشی است؛ رکورد قدیمی حذف، تصحیح عددی یا معتبرسازیِ پسینی نمی‌شود.
- پس از راه‌اندازی، `/api/health`، نسخهٔ backend و صفحهٔ سرو‌شده، همان تنظیمات اسکن و مبنای `heat_basis` بررسی شوند. فعال‌بودن systemd به‌تنهایی پذیرش نیست.
- صفحهٔ قدیمی باید refresh شود. سلامت کندل/قیمت و ردهای داده در وضعیت stream بررسی شوند؛ برای آزمون، سفارش مصنوعی در حساب واقعی ایجاد نشود.
- کاهش تعداد شواهد معتبر می‌تواند نتیجهٔ کنارگذاری legacy IRT باشد؛ حذف داده محسوب نشود و با دست‌کاری تاریخچه جبران نشود.

## ماتریس خطا و rollback

| زمان خطا | اقدام امن |
|---|---|
| پیش از هر تغییر کد/داده | نصب انجام نشود؛ اگر سرویس فقط برای snapshot متوقف شده و state تغییر نکرده، نسخهٔ قبلی مجدداً اجرا و health بررسی شود |
| پس از تعویض source ولی قطعاً پیش از اولین اجرای کد جدید/migration | source قبلی با محیط سازگار برگردد؛ شرط «هیچ writer جدید اجرا نشده» باید قابل اثبات باشد |
| پس از شروع نسخهٔ جدید یا نامعلوم‌بودن آن | برگشت خودکار source و restart ممنوع؛ سرویس متوقف بماند تا snapshot شکست حفظ و تصمیم rollback داده با تأیید کاربر گرفته شود |

### برگشت پس از اجرای نسخهٔ جدید

1. سرویس و تمام writerها متوقف و نبودن writer فعال تأیید شود.
2. **ابتدا snapshot جداگانهٔ post-upgrade** از همهٔ داده‌ها، Paper و `.bak`، WAL/SHM موجود، لاگ‌های لازم و شناسهٔ کد تهیه شود. این snapshot نباید روی backup پیش از ارتقا نوشته شود.
3. اگر سفارش/پوزیشن جدید یا عملیات Live وجود دارد، بازگرداندن snapshot قبلی بدون reconciliation ممنوع است؛ snapshot قدیمی تاریخ بازار یا معاملات واقعی را برنمی‌گرداند. کاربر باید پیامد برگشت را صریحاً تأیید کند.
4. مجموعهٔ سازگارِ کد/محیط/config/state پیش از ارتقا بازیابی شود؛ نه فقط فایل ژورنال یا فقط source. Paper اصلی و `.bak` باید از یک مجموعه باشند.
5. پیش از جایگزینی database، وضعیت WAL/SHM آن کنترل شود: sidecarهای متعلق به state شکست‌خورده، پس از حفظ در snapshot و در نبود تمام writerها، باید از مسیر فعال کنار گذاشته شوند؛ روی database بازیابی‌شده replay نشوند. روی فایل‌های SQLite باز restore انجام نشود.
6. طرح SQLite، integrity، JSON و مالکیت/مجوزها بررسی، سپس نسخهٔ قدیمی اجرا و health/پیکربندی تأیید شود. ردیف‌های post-upgrade در snapshot شکست حفظ بمانند؛ ادغام خودکار با legacy یا حذف آن‌ها ممنوع است.

## شواهد محلی موجود

`server/tests/test_upgrade_rollback_contract.py` دو آزمون آفلاین دارد:

- ساخت طرح ژورنال پیش از قرارداد، backup، migration و درج رکورد جدید، نگهداری snapshot شکست، سپس بازیابی دقیق schema و دادهٔ قبلی؛ رکوردهای پس از ارتقا در snapshot جدا باقی می‌مانند.
- snapshot هم‌زمان Paper و `.bak`، خروج جزئی ساختگی، نگهداری state جدید و بازیابی مجموعهٔ قبلی با heat سازگار.

این تست‌ها فقط روی فایل‌های موقت و دادهٔ ساختگی‌اند؛ نه اجرای نسخهٔ قدیمی روی Python قدیمی، نه اجرای systemd و نه تضمین نصب روی سرور واقعی.

## پذیرش پس از استقرار تأییدشده

یک چرخهٔ طبیعی Paper شامل سفارش، پوزیشن، خروج طبیعی و ژورنال معتبر باید بررسی شود. برای تشخیص، تغییر دستی حدها، افزایش caps، خروج اجباری یا فعال‌سازی Live نمی‌خواهیم. شروع رسمی مشاهدهٔ پنج‌روزه جداگانه تعیین می‌شود؛ legacy خودکار baseline نیست و پنج روز/۳۰ نمونه تضمین سود یا مجوز Live نیست.
