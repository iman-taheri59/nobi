# پشتیبان و بازیابی آفلاین

[English](operations-recovery.en.md) · **فارسی**

> این راهنما دستور اجرای خودکار نیست. سرویس و تمام نویسنده‌های داده باید با برنامهٔ نگهداری و مجوز جداگانه متوقف شوند. بازیابی از وب عمداً غیرفعال است؛ تأیید متنی به‌تنهایی توقف writerها را ثابت نمی‌کند.

## انتخاب منبع و محرمانگی

- پشتیبان Settings از مسیرهای **فرایند در حال اجرا** استفاده می‌کند، نه draft ذخیره‌شده در managed. تنظیم مسیر جدید، فایل DB را مهاجرت نمی‌دهد.
- CLI بدون واردکردن برنامه اجرا می‌شود و `.env` را خودکار نمی‌خواند. برای بازیابی، هر سه مسیر `--journal`، `--auth` و `--live` الزامی‌اند. مسیرها را با وضعیت مؤثر نصب تطبیق دهید؛ پیش‌فرض ریپو جای آن را نمی‌گیرد.
- نبودن/صفر‌بایت‌بودن هر منبع مورد انتظار، backup را متوقف می‌کند. برای عبور از این خطا فایل SQLite خالی نسازید؛ ابتدا منشأ و نیاز واقعی آن دامنه را بررسی کنید.
- فایل zip جدید خصوصی (`0600` روی POSIX) است. پوشهٔ جدید backup نیز خصوصی ساخته می‌شود؛ permission پوشهٔ ازقبل‌موجود و مسیرهای والد باید جداگانه بررسی شود.
- آرشیو سه DB، دادهٔ حساس حساب و هش‌ها را دارد؛ نبود `.env`/کلید API آن را عمومی نمی‌کند. این آرشیو پشتیبان کامل سیستم‌عامل، فایل Paper JSON، کلیدها یا تمام داده‌های برنامه نیست.
- سازگاری snapshot در سطح **هر DB** است؛ snapshot چند DB، تراکنش واحد نیست. برای checkpoint کاملاً هماهنگِ چند دامنه، نویسنده‌ها باید قبل از backup هم متوقف/هماهنگ شوند.
- نام خروجی موجود overwrite نمی‌شود. برای backup بعدی نام/زمان دیگری انتخاب کنید.

## پیش‌شرط‌های بازیابی

۱. آرشیو و مقصد صحیح را خارج از جریان معامله بررسی کنید و وضعیت جدیدتر لازم را جدا نگه دارید؛ restore دادهٔ مقصد را جایگزین می‌کند.

۲. سرویس، worker، scheduler، اسکریپت نگهداری و هر اتصال SQLite دیگر را متوقف کنید. هیچ مسیر Live برای بررسی این راهنما لازم نیست.

۳. اگر فایل‌های `-wal`، `-shm` یا `-journal` باقی است، **آن‌ها را دستی حذف نکنید**. پس از توقف قطعی همهٔ نویسنده‌ها، checkpoint/بستن سالم SQLite لازم است. برای WAL معتبر، اجرای `PRAGMA wal_checkpoint(TRUNCATE)` روی اتصال نگهداری و سپس بستن آن، الگوی معمول است؛ busy یا خطای integrity به معنی ادامه‌ندادن restore است. ممکن است snapshot خواندنی هم sidecar خالی باقی گذاشته باشد. وجود هر sidecar باعث رد محافظه‌کارانهٔ این ابزار می‌شود.

۴. CLI با `--force --offline` و **هر سه مسیر صریح مقصد** اجرا می‌شود. `--offline` صرفاً تأیید اپراتور است؛ ابزار سرویس را متوقف نمی‌کند و ثابت نمی‌کند writer دیگری بعداً شروع نخواهد شد.

۵. manifest، checksum و integrity همهٔ فایل‌های آرشیو، قبل از اولین جایگزینی بررسی می‌شوند. سپس replacement و undo هر مقصد آماده می‌شود. در شکست عادیِ میانی، مقصدهای تغییرکرده برگردانده می‌شوند؛ در شکست خود undo، کپی‌های خصوصی بازیابی نگه داشته می‌شوند و نباید بدون بررسی حذف شوند.

۶. این rollback، **تضمین اتمیک‌بودن در برابر قطع برق، crash فرایند یا چند فایل روی چند دیسک نیست**. پیش از برگرداندن ترافیک، سازگاری دامنه‌ها، schema، حساب و ledger باید در محیط نگهداری بررسی شود. اعتبار manifest/integrity به معنی نسخهٔ درست یا وضعیت معاملاتی هماهنگ نیست.

فرمت قدیمی ۱ فقط journal/auth دارد و Live را جایگزین نمی‌کند؛ آن را بازیابی کامل همهٔ دامنه‌ها ننامید.

نمونهٔ شکل فرمان، با مسیرهای صرفاً نمونه (در این اصلاحات اجرا نشده است):

```bash
python scripts/state_backup.py restore /private/path/snapshot.zip \
  --journal /actual/runtime/journal.db \
  --auth /actual/runtime/auth.db \
  --live /actual/runtime/live_execution.db \
  --force --offline
```

آزمون‌های خودکار فقط DBهای ساختگی در پوشهٔ موقت را جابه‌جا می‌کنند. قبولی آن‌ها مجوز استقرار، توقف سرویس یا بازیابی حساب واقعی نیست.
