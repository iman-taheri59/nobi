# چطور بازهٔ درست `NBX_RR_LEVELS` را تشخیص بدهیم

**فارسی** · [English](rr-ladder-tuning.en.md)

> پیش‌نیاز: [اصلاحیهٔ ADR-0008](adr/fa/ADR-0008-مدیریت-ریسک-و-حجم-دهی-پوزیشن.md) که
> می‌گوید چرا نردبان زنده و نردبان بک‌تست عمداً یکی نیستند.

## پاسخ کوتاه

«بهترین بازه» یک عدد جهانی نیست. چیزی که می‌شود تشخیص داد این است: **آیا یک نردبان
نامزد، بیرون از نمونه با تعداد معاملهٔ کافی و با فاصلهٔ معنادار از بقیه، بهتر عمل
می‌کند یا نه.** اگر داده کم باشد، پاسخ صادقانه «هنوز قابل تصمیم نیست» است — و مخزن
همین را در `gate.state = INSUFFICIENT_DATA` می‌گوید، نه با یک عدد سبز.

## ۱. اول، ریاضیات حداقلی

نردبان یک پارامتر **مدیریت معامله** است، نه یک پیش‌بینی. اثرش در توزیع R-multiple
ظاهر می‌شود، و اختلاف دو نردبان نزدیک معمولاً کوچک است:

انحراف معیار R در معامله‌های واقعی حدود ۱٫۵R است. خطای معیار میانگین با `n` معامله:

| تعداد معامله | خطای معیار میانگین R |
|---|---|
| ۳۰ | ≈ ۰٫۲۷R |
| ۱۰۰ | ≈ ۰٫۱۵R |
| ۴۰۰ | ≈ ۰٫۰۷۵R |

یعنی با ۱۰۰ معامله، اختلاف کمتر از حدود ۰٫۳R (دو خطای معیار) **نویز** است. نتیجهٔ
عملی: بین `(1.2,2.0)` و `(1.5,2.5)` با ۸۰ معامله نمی‌شود داوری کرد. اگر گزارش
بک‌تست می‌گوید یکی ۰٫۰۵R بهتر است، چیزی نگفته است.

## ۲. افق داده — این محدودکنندهٔ اصلی است

سقف کندل در روت بک‌تست **۲۰۰۰** است. معنی‌اش برای هر تایم‌فریم:

| تایم‌فریم | ۲۰۰۰ کندل ≈ | برای داوری نردبان |
|---|---|---|
| `15m` | ۲۱ روز | **نامناسب** — یک رژیم بازار، معامله‌های زیاد ولی بی‌تنوع |
| `1h` | ۸۳ روز | مرزی — وابسته به تعداد معامله |
| `4h` | ۳۳۳ روز | **بهترین گزینه** — چند رژیم، تعداد معاملهٔ کافی |
| `D` | ۵٫۵ سال | خوب برای پایداری، ولی معامله‌های کم |

قاعده: نردبان را روی `4h` تصمیم بگیرید و روی `1h` و `D` **تأیید** کنید. اگر روی هر
سه یکی نبود، نردبان انتخاب‌شده ویژگی همان بازار/دوره بوده است.

## ۳. روش — پنج قدم

### قدم ۱: فهرست نامزدها را کوچک نگه دارید

سه تا پنج نامزد، نه یک پیوستار. پیشنهاد:

| نامزد | `tp1_r, tp2_r` | منطق |
|---|---|---|
| محافظه‌کار | `1.0,1.5` | برد بیشتر، هر برد کوچک‌تر |
| **پیش‌فرض زنده** | `1.2,2.0` | کنترل (baseline) |
| پیش‌فرض بک‌تست | `1.5,2.5` | همان چیزی که شبیه‌ساز ترجیح می‌دهد |
| صبور | `2.0,3.5` | برد کمتر، هر برد بزرگ‌تر |

کاندیدها باید `tp2 ≥ MIN_RR = 1.5` باشند، وگرنه هر پلن زنده برچسب `low-rr`
می‌گیرد و صفحه هم همان را هشدار می‌دهد — یعنی آگاهانه زیر سیاست ریسک کار می‌کنید.

### قدم ۲: بک‌تست گردشی با گرید صریح

گرید پیش‌فرض `DEFAULT_PARAM_GRID` خودش روی `tp1_r/tp2_r` می‌چرخد؛ برای مقایسهٔ
کنترل‌شده، فاصلهٔ حد ضرر را ثابت نگه دارید و فقط نردبان را بچرخانید:

```bash
curl -s -X POST http://127.0.0.1:8000/api/backtest/run \
  -H 'Content-Type: application/json' -d '{
    "symbol": "BTCIRT", "tf": "4h", "bars": 2000,
    "atr_stop_k": 2.0, "slippage_bps": 6,
    "grid": [
      {"atr_stop_k": 2.0, "tp1_r": 1.0, "tp2_r": 1.5},
      {"atr_stop_k": 2.0, "tp1_r": 1.2, "tp2_r": 2.0},
      {"atr_stop_k": 2.0, "tp1_r": 1.5, "tp2_r": 2.5},
      {"atr_stop_k": 2.0, "tp1_r": 2.0, "tp2_r": 3.5}
    ]
  }' | python -m json.tool > btc-4h.json
```

`slippage_bps=6` را صریح بدهید. از ۱.۰.۷ پیش‌فرض همین ۶ bps است، ولی صریح دادنش
دو فایده دارد: خروجی خودش می‌گوید با چه هزینه‌ای ساخته شده، و اگر روزی عدد را عوض
کردید، مقایسه‌های قدیمی و تازه قابل‌قیاس می‌مانند. نردبانی که هدف نزدیک‌تر دارد با
هزینهٔ صفر به‌طور مصنوعی برنده می‌شود — و از ۱.۰.۷ اجرای `slippage_bps=0` دیگر
نمی‌تواند `PASS` بگیرد (`gate.failed` شامل `costs_modeled` می‌شود).

این کار را برای چند بازار و چند تایم‌فریم تکرار کنید — نه یکی:

```bash
for S in BTCIRT ETHIRT SOLUSDT; do for TF in 4h 1h D; do
  curl -s -X POST http://127.0.0.1:8000/api/backtest/run -H 'Content-Type: application/json' \
    -d "{\"symbol\":\"$S\",\"tf\":\"$TF\",\"bars\":2000,\"atr_stop_k\":2.0,\"slippage_bps\":6,
         \"grid\":[{\"atr_stop_k\":2.0,\"tp1_r\":1.0,\"tp2_r\":1.5},
                 {\"atr_stop_k\":2.0,\"tp1_r\":1.2,\"tp2_r\":2.0},
                 {\"atr_stop_k\":2.0,\"tp1_r\":1.5,\"tp2_r\":2.5},
                 {\"atr_stop_k\":2.0,\"tp1_r\":2.0,\"tp2_r\":3.5}]}" \
    > "bt-$S-$TF.json"
done; done
```

### قدم ۳: سه چیز را به این ترتیب بخوانید

هر گزارش سه بخش دارد که باید **با هم** خوانده شوند:

**الف) `gate.state`** — دروازهٔ ارتقای ADR-0009:

| وضعیت | معنا برای این تصمیم |
|---|---|
| `PASS` | همهٔ شرط‌ها با دادهٔ زنده برقرار است → قابل استناد |
| `FAIL` | یکی از شرط‌ها رد شده؛ `gate.failed` می‌گوید کدام |
| `INSUFFICIENT_DATA` | کمتر از ۳ پنجره یا کمتر از ۳۰ معاملهٔ بیرون‌نمونه — **هنوز قابل تصمیم نیست**؛ `gate.bars_needed` می‌گوید چند کندل لازم است |
| `SYNTHETIC_DATA` | کندل‌ها از fallback شبیه‌سازی‌شده آمده‌اند؛ هیچ تصمیمی بر آن مجاز نیست |

**ب) `param_stability`** — مهم‌ترین شاهد برای این پرسش:

```json
"param_stability": {"distinct_param_sets": 3, "most_common_share": 66.7}
```

یعنی دو سوم پنجره‌ها مستقل از هم همان نردبان را انتخاب کرده‌اند. تفسیر:

- `most_common_share ≥ 60٪` → نردبان پایدار است؛ کاندید جدی.
- `30–60٪` → بی‌ثبات؛ بازار بین دو حالت مردد است.
- `< 30٪` → هر پنجره چیز دیگری می‌خواهد؛ **پیش‌فرض را نگه دارید**.

**ج) `aggregate`** — و فقط بخش بیرون‌نمونهٔ آن: `expectancy_r`، `profit_factor`،
`max_drawdown`، `profitable_windows`. عدد درون‌نمونه (`is`) را برای انتخاب
استفاده نکنید؛ همان چیزی است که نردبان رویش برازش شده.

### قدم ۴: توافق بین بازارها، نه قهرمانی در یک بازار

هر جفت (بازار، تایم‌فریم) یک رأی دارد. شرط پذیرش پیشنهادی:

- نردبان در **دست‌کم نیمی** از جفت‌ها در بهترین یا دومین جایگاه باشد،
- و هیچ جفتی با آن `gate.state = FAIL` ندهد.

اگر تنها در یک جفت اول شده، آن یک ویژگی همان بازار است، نه یک سیاست.

### قدم ۵: فلات، نه قله

نردبانی را بردارید که **همسایه‌هایش** هم قابل قبول‌اند. قلهٔ تیز (مثلاً `2.0/3.5`
عالی و `1.5/2.5` فاجعه) معمولاً یعنی برازش روی نویز. فلات یعنی خطا در انتخاب،
هزینهٔ کمتری دارد.

## ۴. جدول تصمیم

| یافته | تصمیم |
|---|---|
| `INSUFFICIENT_DATA` در بیشتر جفت‌ها | تغییر ندهید؛ `bars_needed` را برآورده کنید (تایم‌فریم بالاتر یا تاریخچهٔ بیشتر) |
| `param_stability` پراکنده | تغییر ندهید؛ پیش‌فرض `1.2,2.0` |
| یک نردبان پایدار، `PASS`، و در ≥ نیمی از جفت‌ها برتر | همان را با `NBX_RR_LEVELS` تنظیم کنید |
| نردبان برتر `tp2 < 1.5` دارد | رد کنید؛ زیر `MIN_RR` می‌رود |
| نردبان برتر فقط با `slippage_bps=0` برنده است | رد کنید؛ با ۶ bps برنده نیست یعنی هزینه آن را می‌خورد |

## ۵. پس از پذیرش

```bash
# در env سرویس (systemd: /etc/nobi/nobi.env)
NBX_RR_LEVELS=1.5,2.5
# restart، سپس تأیید:
curl -s http://127.0.0.1:8000/api/risk/state | python -m json.tool | grep -A3 rrLevels
```

و بعد **قاعدهٔ بازگشت را از قبل بنویسید** — وگرنه تغییر تا ابد می‌ماند:

- اگر پس از ۳۰ معاملهٔ بسته‌شدهٔ زنده، `expectancy_r` منفی بود، به پیش‌فرض برگردید.
- ژورنال `r_multiple` هر معامله را نگه می‌دارد؛ `/api/journal/summary` همان است که
  باید قضاوت نهایی را بر آن بگذارید، نه بر گزارش بک‌تست.

## ۶. چیزی که این سند نمی‌گوید

این روش، «بهینهٔ» نردبان را پیدا نمی‌کند و ادعا هم نمی‌کند. کاری که می‌کند این است
که مانع شود یک عدد از گزارش بک‌تست، بی‌شاهد، رفتار معاملاتی زنده را عوض کند.
اگر داده کافی نیست، پاسخ درست «هنوز نه» است — و مخزن همین را می‌گوید.
